# 条件生产段：续种回款后再转产

## 修改依据与范围

前一轮调查见 [根因记录](event_menu_root_cause.md)：完整菜单确实把合法的 `cycles=2` 全部筛掉；Keep 会消耗普通事件名额，并不等于等待条件后重访。现有执行器本来就支持批次、混合路线及作物续种，本次复用这些能力。

本次补通“有条件兑现的下一批安排”，对应 DECEM 回放里的续种、条件转产和资金周转；没有推断其训练算法。单局事后赢家不可预测、微小预测分差缺少校准、组合行为未稳定泛化等问题仍然存在，本次不能宣称全部解决。

## 真实执行语义

`plan_events::Choice.conditional` → `Controller::revise_batch_mode` → `Stage.conditional` → 共享 `Schedule` → 原有执行器。

例如：当前两格小麦临近收获，选择 `next=SHEEP, cycles=2, conditional=true`：

1. 当前小麦收获后续种一次，再完成一轮收获。`cycles=2` 是从当前状态计两次收获，不是额外续种两次。
2. 临近转换窗口，预算预留羊和首批饲料。原有种植、养护、工资等维护先执行；采购只用已到账现金，命令发出不算已获得库存。
3. 动物库存、可分配饲料、运营现金底线、当前可用工时同时满足后，在可收获/空地边界切换。不会为了切换清掉等待期中已经续种的未成熟小麦。
4. 不满足就保留原作物的项目，允许继续续种、回款。不能保证无现金、无种子时也凭空生产；已有真实路线预约同样不能被抢占。
5. 新条件批次持续保有自己的后续修订机会；资金/库存/工时/市场条件真实变化才产生事件。同一状态不会因为 Keep 重复调用网络。只拥有该批次，不接管无关地块。
6. 部分修订保留未改动地块；季末无法完成的未来生产退出，真实作物、库存和已花成本保留。

当前工时仍是包含路线占用、行走、放置及基础服务的保守估计，并非未来整季的精确排程。动物首批饲料保留每格两单位小麦，后续仍由原维护系统供给。

## 菜单与学习

最多四项，仍逐项真实执行到第720回合：

- 第0项保留冻结旧底座的确切动作；新条件批次内部第0项是保留当前承诺。
- 初次事件保留明确 Keep。
- 优先配对“现在转动物”和“再续种一轮后转同种、同数量动物”，不让短期价格排序淘汰全部延后方案。
- 后续菜单有位置时补缩小批次、取消或作物安排。数量、品种仍是有限候选，**并非每种商品、所有数量都在每次菜单中出现**。动物品种覆盖使用公开商店需求及当前季节时间，未使用隐藏随机种子。
- 新特征明确条件计划标记、公开商店对目标产品的需求；现有资金、库存、工时、生产承诺特征继续使用。

采集、验收、部署使用同一候选及执行器。条件方案之外，终局分支仍由固定已验收策略续接；旧续接策略会保留新条件批次，让其执行器自动检查并兑现，不会用旧的修订语义覆盖它。新策略整局运行时可以继续修订自己的条件批次，其组合效果必须经过独立整局验收。局部标签不是这些组合必然有利的证明。

目标仅终局比赛得分；未加入现金、产量或“多转产”奖励。集合不完整时不训练，不扩大每局模拟预算。没有恢复高频独立交易、周期替换续接网络或直接让网络接管全部经营。

## 兼容性

新检查点 `event-policy-iteration-v10`，条件策略合同 `event-conditional-batch-menu-v1`，新集合及特征合同；旧经验、Adam 和失败提议网络不迁入。

脚本从 `runs/event_policy_complete_sets_trial/best.json` 导入**已验收**部署。当前该文件仍是旧协议 revision=1，不是失败的第20轮提议权重。旧部署先保持原样，新菜单网络从零修正头开始。

- v10 `--resume` 可以恢复完整训练状态，输出使用新目录。
- v9 已验收菜单策略仍可按原协议由 `event-agent` 部署；不将其权重静默当作新特征解释，因此此类检查点不能直接初始化本实验。当前脚本源不属于此情况。
- `--followup-scope single` 保留旧动作的单次修订语义；选中新条件计划才获得该批次持续责任。不是全局扩大旧底座范围。

## 实验命令

本机已构建。若换机器或改代码，先构建：

```bash
export PATH="/tmp/route-rl-rustup/toolchains/stable-x86_64-unknown-linux-gnu/bin:$PATH"
export CARGO_HOME=/tmp/route-rl-cargo
cargo build --manifest-path native/Cargo.toml --release --features train --offline --bin event-train --bin event-agent -j 4
```

运行20轮（前台运行，可放在screen中）：

```bash
bash tools/run_conditional_trial.sh
```

可传新输出目录：`bash tools/run_conditional_trial.sh runs/event_policy_conditional_trial2`。完整参数就在脚本里。20轮为160个训练条件，320条基础轨迹，另加预算内终局分支和评估。训练/固定观察/独立确认种子隔离。

查看：

```bash
tail -f runs/event_policy_conditional_trial/train.log
```

重点看 `observations.jsonl` 中同种子对照得分变化、`evaluations.jsonl` 的独立复核；`comparisons.jsonl` 的 `candidate_plans` 应出现 `conditional=true, cycles=2`。候选出现、loss下降、转产变多都不等于比赛能力提升。

## 本次验证（不是收益证明）

- 138项库测试、16项训练测试、5项部署测试通过；新增缺工时、条件事件重访和持续缺款真实续种后，8项针对性测试通过（其中包含7项条件计划测试）；最后的完整菜单采集/恢复统计回归也通过。
- 真引擎确认两格小麦续种一次后转羊并产出；缺现金、饲料、工时时不提前切换；同一状态不重复重访，真实资金及到货变化能重访。
- 720回合零修正头与旧策略动作一致；旧部署协议保留；完整集合、终局预算、独立种子、恢复与经验失效回归通过。
- `/tmp/event_conditional_smoke`：2个条件，4个完整菜单、16条终局分支，CUDA更新与保存成功；约55秒采集、0.33秒更新（同时运行了测试，不能用作正式速度基准）。初始模型不改变已验收动作。未把这1轮当成胜率提升证据。
- 补正旧诊断的缺字段误报：`candidate_coverage`按完整集合去重，记录真实候选数；`all_conditional_execution`按菜单顺序记录条件地块、成功转产、产出和过期数。这些仍只是执行诊断，不作为奖励。
