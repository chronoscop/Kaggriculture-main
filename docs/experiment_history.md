# 历史实验与失败教训

本文压缩归档早期 Python 路线预训练、Rust mixed/plan/event 实验及最后的学习审计。当前可用的 BC 流程见 [README](../README.md) 和 [BC 指南](action_bc_pipeline.md)。这里的旧训练建议、参数与检查点格式属于各自历史版本，不是当前 BC 的运行说明。

历史实验实现了生产执行、共享路线、资源账本和终局对照，也有局部进步；**没有证明最终事件学习器能稳定掌握条件化连续经营，或达到 farm2945 的对战目标。** 这项结论针对旧实验，不用于否定当前 BC 的可运行性；当前 BC 的比赛效果仍需独立评估。

## 如何理解证据

- **实测事实**：来自固定版本日志、完整回放、同状态分支或独立对局，必须保留种子与样本边界。
- **结构限制**：来自当时的实现，例如候选被筛掉、执行范围与训练范围不一致。复用诊断前必须检查当前代码。
- **因果假设**：信息不足、优化、表征或标签噪声等可能解释。没有对照时，不能把某个猜测当作已解决的根因。

当前 event 目标是第 720 个状态的比赛得分：胜=1、平=0.5、负=0。现金、现金差、工作量和产量只是诊断，不作辅助奖励或晋级硬否决。早期部分 mixed/proposal 文档使用其他回报口径，不能继续用于当前目标。

## 比赛回放证据

压缩自原 `competition_replay_review.md`，审计日期 2026-09-27；范围是 market3 rule100、learned50、历代 v7 和五场 DECEM 回放。

五场 DECEM 记录显示：前两天形成 25 格生产；收获后成功续种分别 183、212、197、222、192 次，间隔中位数均为 1 回合。可见作物间切换、作物转养、畜牧退出后重种，以及取料、喂养、收肥、施肥、收获、续种共用路线。不同商店条件下后续投入不同，季末停止无法兑现的新生产。

这些记录支持四项行为目标：**连续生产、条件续种/转产、共享材料与工作路线、现金周转**。回放不能证明 DECEM 使用了哪种训练算法；五场并非随机样本，不能估计总体胜率。仓库内 farm2945 是另一份参考 agent，不能当作 DECEM 源码。

同种子 80000991 换座，三个旧 mixed 模型对 farm2945 共六局均输；生产峰值约 10–15 格，无扩地，rule100/learned50 几乎没有续种。它们只有一个独立种子，是机制诊断，不是总体实力排名。

当时 mixed 的结构限制包括每天最多两个启动/转产项目、25% 扩张采购预算、较窄的雇工/地块候选，以及按工作次数预筛路线、缺少按商品划分的产出表示。**后来 plan/event 已有批量生产、经济路线和两阶段转产，不能把这些旧限制直接当作当前失败原因。** 后来的示例局已续种 199 次、间隔中位数 1 步，说明连续执行与条件选择需要分别检查。

原始证据曾保存在 `replay/` 和 `runs/competition_replay_review/`，包括逐步回放、行为汇总和经验保持审计。这些目录不随 Git 分发。

## plan_compare 的全局接管失败

压缩自原 `plan_compare_trial_review.md`。`runs/plan_compare_trial` 的100轮包括1,600局基础对局、3,191条分支、2,875组有效对照，零晋级；`best` 与 `initial` 权重相同。

| 轮次 | 固定16局平均终局现金 | 对战得分率 |
| --- | ---: | ---: |
| 0 | 51,912.38 | 50% |
| 10 | 48,178.38 | 0% |
| 30 | 19,651.38 | 0% |
| 100 | 16,645.88 | 0% |

第一轮32个探测点在40–572回合，没有覆盖前24回合开局；29个有效标签中17个支持在已有生产时暂缓新增。初始零评分头依赖平手选首项，尚未学会开局。第一次更新改变了未覆盖局面的排序，第二轮16局全部零生产、零收获，平均现金2,976。

每局只测两个状态、各一个替代，部署却在全局约360个经营时点的全部候选中 argmax。局部标签只回答固定继续策略下的 A/B 优劣，不能支持未测候选、未覆盖开局或很多改动组合后的整季行为。完整失败只阻止覆盖 best，退化网络仍继续主导采集与近期对手。

原准确率把平手记0.5，推理却固定选首项；修正后第一轮实际选择准确率更新前后都是19/29。统计修正不解决策略退化。第10轮123个旧优秀对照的排序准确率，随10/30/100轮网络从62.60%到72.36%、76.42%，整局仍变差，排除了“只要保住局部排序就能保住整季”的想法。

由此保留：冻结已验收行为产生主要状态；训练覆盖接管范围；先形成有限的完整候选策略，再用训练外配对初筛和另批独立种子复核；失败候选不能自动接管整局。

## event 的设计与执行边界

本节归档原 `event_plan_next_steps.md` 及后续事件协议设计。最初提案不是启动新实验的指令；哪些能力已经实现，以当前 `native/src/` 为准。

事件系统补入同一批次的身份/阶段、共享现金/物料/工时账本、到货/收获/服务延期事件，以及尚未执行的下一批修订。当前生产、已付款材料和在途任务保留真实状态；未来回款不能提前支出，采购请求不等于到账。路线可服务多个生产计划，但未来工时仍是估计，并非精确跨季排程保证。

网络为有限的可执行菜单评分，规则底座负责开局及声明范围外的经营，执行器负责采购与工作。网络没有从零学会所有生产，也不自由生成任意路线。最终 contextual 菜单最多六项；当前完整菜单训练是相对候选评分学习，不是早期 mixed 逐动作 PPO。

最终协议在一个周期内冻结已验收参考和继续策略，从参考/候选真实前缀取状态，对菜单全部方案执行到终局。核心损失是所有有效非参考项的平均：

```text
[(log π(j) − log π(0)) − (score(j) − score(0))]²
```

采集、标签、执行和部署使用同一菜单与声明范围。通过整局独立确认才推进部署，继续策略变化后使依赖旧版本的标签失效。不能只升级版本名、扩大对手池或增加动作来替代这条闭环。

执行审计还留下两项必须保留的约束：

- 第一次配对 smoke 有11个后续比较，却全部只有 Keep/Cancel，因为日工在维护重新雇用前已到期。必须使用维护后的真实观察，不虚构未来工人；真实持续缺工时仍保留取消。
- 被路线暂时阻塞的同批次后续事件必须活到该批次可编辑，不能被普通 scope 耗尽删除，或被日常 dispatch 抢走预留机会。

时序/执行变化必须版本化并使依赖标签失效；已验收旧事件 scope 保留旧解释，不能静默重解释检查点。

## 后续必须保留的教训

1. 核对当前代码再复用旧诊断；区分实测、结构限制和因果假设。
2. 采集谁、比较谁、标签依赖哪份继续策略、最终执行什么，必须一致。新学习器不能因少量局部样本自动接管整局。
3. 检查真正的合法候选，不只看事件数量；资源、路线、真实到货及后续机会都影响选择空间。
4. 不按事后赢家分配经验名额，不把失败/中性数据全部丢掉；经验在库里也要检查实际学习权重。
5. 参数更新、loss、局部排序、执行完成率、现金和GPU利用率，都不能单独替代独立完整比赛结果。
6. 保留冻结已验收部署与旧检查点；验证种子不参与训练，固定选模面板之后另做配对独立确认。
7. 时序、执行、编码或目标变化时版本化契约，从实际终局重算依赖标签。不能声称不兼容检查点可原样恢复。
8. 换版本名、对手池、动作数量或延长训练，不是具体缺失能力的解释。连通性修复不能为经济改善背书。

历史诊断多次过早转成夜训建议，给实验增加了时间和服务器成本。今后应先用明确的执行/学习检查证明修复范围，再让训练结果回答经济效果；不能承诺长训单调改善。

本文件合并原 `project_retrospective.md`、`competition_replay_review.md`、`plan_compare_trial_review.md`、`mixed_v*.md`、`plan_*.md`、`event_*.md`、`conditional_execution_audit.md` 和 `contextual_learning_final_audit.md`。重复实现说明、过时长训命令和临时机器路径不再单独保留。历史原文仍可从 Git 查阅，例如：

```bash
git log --all -p -- docs/plan_compare_trial_review.md
```

原始实验需要匹配当时的源码、manifest、权重、指标、回放和契约；不能把历史命令直接套用当前入口。`runs/`、`replay/`、`models/`、`data/` 和编译产物被忽略，文档归档不包含模型或日志备份。删除旧文档没有删除这些本地实验产物。
